# v1.1.3 Research Findings

Date: 2026-05-23

## Executive Summary

JasperLoop-DV is a JasperGold-in-the-loop AI design-verification copilot prototype. Its core boundary is that the LLM proposes structured DV artifacts and next actions, while JasperGold remains the formal oracle when syntax, proof, cover reachability, counterexample, or vacuity checks are actually run.

Through `v1.1.3-local-qwen-jasper-recheck`, the project has a complete evidence chain for one important workflow: local Qwen generated real SVA repair outputs, the output mechanics gate measured schema/fallback/hallucination behavior, the full local benchmark preserved saved SVA repair finals, and those saved final candidates were re-checked with JasperGold on Moore.

The main result is that the local Qwen/Qwen3-14B-AWQ full benchmark passed the output-mechanics gate, and 22 of 23 saved SVA repair final candidates passed JasperGold syntax and proved under the project harnesses. The main limitation is that this is not full semantic intent equivalence, and failure triage remains weak on assumption/vacuity cases.

## Evidence Chain

```text
local Qwen real output
  -> schema-constrained output mechanics gate
  -> full local benchmark
  -> saved SVA repair final candidates
  -> JasperGold syntax/proof/vacuity re-check on Moore
  -> curated summaries only, with raw artifacts ignored
```

This chain matters because it separates three different kinds of evidence:

- real local LLM behavior: whether a backend can produce valid structured DV outputs without fallback;
- task-level evaluation: whether the proposed repair, triage, or coverage action matches local expected labels or templates;
- formal-tool re-check: whether saved SVA candidates compile and prove under the configured JasperGold harnesses.

## Important Case Analysis

### `repair_fifo_reset_wrong_polarity`

The full local Qwen SVA repair run already reported a hallucinated signal, `out_valid`, for this case. The JasperGold re-check then failed syntax for the saved final candidate. This is the cleanest example of why hallucinated-signal measurement belongs in the benchmark gate: the static output-quality metric predicted a formal-tool failure mode.

### `repair_arbiter_single_req1_wrong_grant`

This candidate failed the local exact-template match but proved under JasperGold. That does not mean the exact-match metric was wrong or that the candidate is fully intent-equivalent. It means proof and template-level intent alignment are separate signals. The candidate may be a valid alternative property under the checked harness, but it still needs human intent review.

### Assumption/Constraint Triage Weakness

Failure triage remains the main model-quality weakness. In the full local Qwen run, only 3 of 12 gold `assumption_constraint_bug` cases were classified correctly. Several were classified as `assertion_property_bug`, with the recommended action shifted from `fix_assumption_constraint` to `fix_assertion_property`.

This is a research-relevant failure, not a backend failure. The model can produce valid JSON and avoid signal hallucination while still choosing the wrong root-cause category when the distinction depends on assumptions, overconstraint, or vacuity evidence.

## Supported Claims

- JasperLoop-DV demonstrates a working model-agnostic LLM backend route through `JASPERLOOP_LLM_CMD`.
- Local Qwen/Qwen3-14B-AWQ can produce schema-valid DV outputs under structured prompts for the local SVA repair, failure triage, and coverage closure tasks.
- The evaluation stack measures JSON validity, fallback rate, LLM error rate, hallucinated-signal rate, and task accuracy separately.
- The artifact policy and result naming keep deterministic scaffold, real LLM, and JasperGold-backed evidence separate.
- JasperGold re-check confirms that 22 of 23 saved local Qwen SVA repair final candidates compile and prove under the project harnesses used on Moore.
- The re-check also catches a concrete hallucinated-signal failure that local exact-match metrics alone would not fully explain.

## Unsupported Claims / Non-Claims

- This is not Codex CLI performance. The Codex Windows app package route remained blocked from Python subprocess in this environment.
- This is not an official FVEval reproduction.
- This is not production-ready DV signoff.
- A JasperGold proof pass is not proof of full semantic intent equivalence.
- The JasperGold-backed result applies to saved SVA repair final candidates only, not to failure triage or coverage closure outputs.
- This does not show that larger models are required, better, or sufficient.
- This does not prove that the project generalizes to arbitrary RTL beyond the checked benchmark scope.
- This does not make author-provided labels independently discovered truth.

## Research Contribution Framing

The project is more than "AI reads JasperGold logs" because it builds a controlled evidence and evaluation loop around LLM assistance:

- Outputs are schema-constrained and parsed before being scored.
- Triage uses an explicit issue taxonomy and allowed next-action set.
- Signals are checked against allowed design signal lists, and hallucinated signals are measured.
- Deterministic fallback is visible and counted, not silently reported as model success.
- Raw logs, traces, model outputs, and JasperGold report trees stay out of git by default.
- Curated summaries distinguish local scaffold, real LLM, replay, and JasperGold-backed rows.
- JasperGold re-check is applied to saved candidate artifacts, tying model output to formal-tool evidence without treating the model as an oracle.

This framing supports a narrower and defensible research claim: structured formal evidence and formal re-check can make LLM-assisted DV workflows more auditable than raw prompting.

## Next Research Tasks

1. **Assumption/vacuity triage improvement.** Add stronger structured evidence for assumptions, overconstraints, vacuity, and unreachable goals, then measure whether the triage agent improves on the 3/12 assumption-constraint result.
2. **JasperGold-backed re-check expansion.** Extend formal re-check beyond SVA repair to saved SVA generation outputs when those artifacts exist. Keep triage and coverage separate because they are recommendations, not assertions.
3. **Official FVEval-compatible evaluation.** Import and run the official data and equivalence flow only if the exact task definitions and formal metrics are available. Until then, keep local FVEval-compatible scaffolds clearly labeled.
4. **Better intent-equivalence metrics for SVA repair.** Study cases like `repair_arbiter_single_req1_wrong_grant`, where proof passes but exact-template match fails, and develop metrics that separate acceptable alternative properties from weak or intent-mismatched assertions.
5. **Reproducible model/backend packaging.** Package the local vLLM/Qwen route, backend contract, raw artifact handoff, and JasperGold replay steps so another environment can reproduce the same chain without committing raw model or EDA outputs.

## Final Claim Boundary

JasperLoop-DV is a research prototype showing that schema-constrained LLM outputs, explicit DV task taxonomies, output-quality gates, artifact discipline, and JasperGold re-checks can form an auditable AI-assisted DV workflow. Through v1.1.3, local Qwen/Qwen3-14B-AWQ produced structured outputs for SVA repair, failure triage, and coverage closure; the saved SVA repair final candidates were re-checked with JasperGold on Moore, where 22 of 23 compiled and proved under the project harnesses. These results support the feasibility of a JasperGold-in-the-loop AI DV copilot, but they do not establish Codex CLI performance, official FVEval performance, production signoff, or full semantic intent equivalence.
